# Decisions

One line per decision, with the reason. Newest last.

- Pin Codex at `806d973` (your checkout's HEAD, `c3d3b14` plus one code-mode-only commit): the verified facts still hold and provenance matches the checkout.
- Copy from a `git archive` export in `~/.cache/ether/codex-806d973`: `CODEX_SRC` is never written and untracked files never leak in.
- Target is `ether` (workspace `ether`); new crates will be `ether-engine`, `ether-llm`, `ether-tui`, `ether-cli`. Copied crates keep their `codex-*` names until a rename you approve.
- Crates already in Codex's `Cargo.lock` count as approved dependencies; anything else needs your approval.
- `Cargo.lock` is re-seeded from Codex's lock before every `cargo check`: every dependency resolves to the exact version Codex ships.
- Toolchain 1.95.0, edition 2024, Codex `rustfmt.toml`, `clippy.toml` (minus the sqlx rules) and `[workspace.lints]`: copied code builds and lints as it does upstream.
- Only the `dev` and `release` profiles are kept: `dev-small`, `profiling` and `ci-test` serve Codex CI.
- No tests (your instruction): nothing is written, copied or run. Copied crates lose `#[cfg(test)]` items, `*_tests.rs` files, `tests/`, `benches/`, insta `snapshots/` and dev-dependencies. The check is building and running the binary.
- Linux and macOS only: Windows-only code (`cfg(windows)`, `cfg(target_os = "windows")`, `cfg(all(windows, ...))`) and Windows-only dependency tables are stripped from copied crates. Linux gets checked later on a Linux machine.
- `BUILD.bazel` files are not copied: ether builds with Cargo only.
- The mechanical cuts are scripted (`scripts/strip-cfg.pl`, `scripts/orphans.pl`, `scripts/toml-strip.pl`) so they can be reapplied to a newer Codex.
- Layout is `crates/<codex dir>`. `ext/items` becomes `crates/extension-items`; `vendor/bubblewrap` becomes `crates/vendor/bubblewrap`, so `bwrap/build.rs` is unchanged.
- `vendor/bubblewrap` keeps its own LGPL-2.0-or-later licence (`COPYING`); its `tests/` are not copied.
- C1: keep `codex-extension-items` (used by protocol, tools and rollout; 172 lines).
- Sandboxing has no managed network proxy: network access is on or off per the permission profile, enforced by Seatbelt (macOS) and the Linux helper. Reason: network-proxy is on the never-copy list and proxy filtering is out of scope.
- The realtime/guardian/cyber-access protocol types stay until the Phase 3 engine port, which rewrites `Op`/`EventMsg` handling anyway (cut was over the 30-site limit).
- Linux-only crates are type-checked from macOS with `scripts/check-linux.sh` (`aarch64-unknown-linux-gnu` target, bubblewrap C build skipped, blake3 in pure-Rust mode). Crates that compile C for the target (zstd, tree-sitter) wait for a real Linux machine.
- File rewrites that add notes go through `scripts/note.pl`, never through the 50 KB-capped tool read (two files were truncated once and rebuilt from source).
- The new wire API is spelled `wire_api = "chat_completions"` (`WireApi::ChatCompletions`); plain `"chat"` stays rejected as an unknown variant, so old Codex configs fail loudly rather than silently changing meaning.
- C2 detail: the ported `LocalFileSystem` has no sandboxed helper process; filesystem calls run in-process and write permission is checked by the engine before a patch is applied (as Codex core already does).
- C2: copy exec-server's `local_file_system.rs` and `local_file_system_read.rs` into `codex-file-system` as its local implementation.
- C3: drop rollout's SQLite state (`state_db.rs`, `sqlite_metrics.rs`, SQLite-only parts of `metadata.rs`); listing and replay use JSONL files only.
- C5: carry only the crossterm `[patch.crates-io]` fork; the tungstenite patches are dropped because no websocket code is copied.
- C6: drop dev-dependencies on crates not on the list. All dev-dependencies are removed anyway now that tests are gone.
- Phase 3 engine is new code shaped like Codex core, lifting functions and match arms where they stand alone: core's files reach into `Session`, config, guardian, hooks, analytics and exec-server almost everywhere, so they cannot be copied whole. The to-do list is `docs/PHASE3.md`.
- C4: the process backend is a small local one on `codex-utils-pty` (spawn, stdin, output, kill), with the `codex-sandboxing` transform applied before spawn; exec-server's local backend (~4.5k lines) is not copied and shell snapshots are left out.
- Config lives in `~/.ether/config.toml`, with an optional project `.ether/config.toml` and CLI overrides on top; `codex-config` is not copied.
- The Phase 3 runnable is a plain-text `ether` command (prompt in, streamed answer and tool activity out); the Phase 5 TUI replaces it.
- `ether --replay FILE` feeds recorded Responses SSE through the real parser in place of a network model. It is a runtime feature for running the binary before Phase 4 connects GLM, not a test.
- No Windows code is ported (your instruction, Phase 3): new crates have none, and Windows-only modules left in copied crates (PowerShell/cmd, Windows sandbox level, Windows command rules) are removed.
- The engine keeps its own `ModelProfile` (slug, context window, truncation, reasoning and parallel-call support) instead of Codex's `ModelInfo`: no engine event needs `ModelInfo`, and its ~45 fields describe OpenAI's catalog. Defaults follow Codex's fallback for unknown models (272k window, 95% usable, 10 KB truncation). Phase 4's GLM catalog entry goes here.
- The Responses client sends the standard `instructions` field for the base prompt, as plain OpenAI-compatible endpoints expect; Codex instead prepends it as a message.
- ether authenticates with API keys only: the built-in `openai` provider reads `OPENAI_API_KEY` (Codex's expects a ChatGPT login).
- HTTP error statuses become `ApiError::Api` with the server's message and are not retried at the stream level; the HTTP layer already retries 5xx.
- `ether-llm`, `ether-engine` and `ether-cli` are not in `scripts/check-linux.sh`: reqwest's TLS stack (`ring`, `openssl-sys`) compiles C for the target, so they wait for a Linux machine like the zstd and tree-sitter crates.
- Sessions are recorded with `codex-rollout` under `$ETHER_HOME/sessions`, in paginated history mode: ether emits `ItemCompleted` user/agent items, not the legacy `UserMessage`/`AgentMessage` events, and listing needs a user message to find a session.
- The rollout file is created when the first turn starts (as Codex defers it), so a session with no turns leaves no file; the CLI waits for `ShutdownComplete` so the writer is drained before exit.
- Rollout write failures are logged with `tracing::warn!` and never end the session; a rollout that cannot be opened leaves the session unrecorded.
- History items are written to the rollout as stored (after truncation), so resume replays them without truncating again; outputs added for interrupted calls are written too, and a resumed session closes any call still open.
- Resume keeps the current configuration (model, cwd, policies) and takes only the thread id, history, token info and turn counter from the rollout; rollback and compactions without replacement history are not reconstructed.
- `--last` picks the newest session recorded in the working directory, as Codex's `resume --last` does.
- `apply_patch` is advertised as a JSON function tool taking the whole patch as one `input` string (what GLM needs); GPT-5 slugs get Codex's freeform (Lark grammar) tool instead. The handler accepts both call shapes whichever is advertised.
- Patches are checked with Codex's `assess_patch_safety` against the permission profile of the session's `SandboxMode` (cwd as the workspace root, plus `TMPDIR`), then applied in-process on `LOCAL_FS` (C2). Because no sandbox backs the write, "inside the writable roots" is the whole check; Codex's extra "a platform sandbox exists" condition is dropped.
- Patch approvals honour `Approved`, `ApprovedForSession` and `ApprovedExecpolicyAmendment` as a one-off approval; ether does not cache per-path session approvals for patches yet. Every other decision, and a dropped request, reports `PatchApplyEnd` with `Declined` and tells the model "patch rejected by user".
- The turn diff lives on the `Session`, keyed by turn id, and `TurnDiff` is emitted once at the end of each sampling request whose patches changed it (Codex also emits it after each patch).
- `view_image` resizes and encodes the image in the handler with `codex-utils-image` (high-detail limits) and returns it as an `input_image` content item; it is advertised to every model because `ModelProfile` has no input-modality list yet. `codex-utils-image` keeps its own process-wide LRU cache; that cache is in the library, not engine state.
- `request_user_input` is available in every turn and always blocking, since ether has no collaboration modes.
- `apply_patch` invoked through a shell heredoc is handled by `tools::apply_patch::intercept_apply_patch`, which the exec_command handler can call; until it does, it is marked `allow(dead_code)`.
- World state is three sections (AGENTS.md, permissions, environment) in Codex's order, rendered in full on the first turn and as appended diffs afterwards; snapshots live in the session and are compared by value (no Codex hashes or JSON merge patches, which only serve rollout persistence).
- The environment section carries cwd, shell and the local date (`%Y-%m-%d`, as Codex); a day change appends `<environment_context>` with only `<current_date>`. No timezone, network or filesystem details.
- Permissions text uses Codex's bundled templates for sandbox mode and approval policy, plus writable roots; exec-policy approved prefixes, `request_permissions`, auto-review and denied-read lists are left out until ether has them.
- AGENTS.md discovery walks from the git root (`codex_git_utils::get_git_repo_root`) to cwd, preferring `AGENTS.override.md`, with Codex's 32 KiB budget; `$ETHER_HOME/AGENTS.md` comes first. No fallback filenames or project-root marker config.
- Compaction triggers as in Codex: before a sampling request when the last request's `total_tokens` reached `usable_context_window()` (at turn start, or mid-turn when the model still needs a follow-up). After compaction the last-usage figure becomes a byte estimate of the new history so compaction does not repeat.
- The compaction request is Codex's local one: same instructions, no tools, no reasoning settings, history plus the summarization prompt; its output is not recorded, only the summary. Its prefix differs from the turn requests (no tools), so it is a prompt-cache miss, as in Codex.
- Compacted history is Codex's `build_compacted_history`: recent user messages (20k-token budget), a fresh full world-state render inserted before the last real user message, then the summary; the fresh render becomes the new diff baseline.
- `Op::Compact` runs as its own turn (TurnStarted, compaction, TurnComplete).
- Compactions are written to the rollout as `Compacted` items with their replacement history, and world-state items go through the rollout like other history, so resume rebuilds what the model saw. On resume the world-state baseline is not rebuilt, so the first resumed turn appends the full environment and permissions context once.
- Exec approvals follow Codex's exec-policy heuristics with no `is_known_safe` list (Codex 806d973 has none): `never` runs everything in the sandbox and forbids dangerous commands (`rm -f`…); `on-request` runs in the sandbox without asking and asks only when the model sets `sandbox_permissions: "require_escalated"` (with `justification` as the question), and returns sandbox-denied output to the model so it can re-request with escalation; `untrusted` asks for every command not allowed by a rule; after a fast sandbox denial it retries without the sandbox, asking first only if the command was not already approved (a rule-allowed command), as Codex's orchestrator does. `ApprovedForSession` is remembered per session keyed by canonical command, cwd, tty and sandbox permissions; denial, abort, a dropped request or an interrupted turn become a model-visible rejection.
- Exec-policy rules load from `$ETHER_HOME/rules/*.rules` (Codex's file format, read once per session; a bad file is logged and ignored). There are no config layers, requirements overlays or rule amendments.
- On Linux the sandbox helper is `codex-linux-sandbox` next to the `ether` executable; if it is missing, sandboxed commands fail with a model-visible error suggesting `--sandbox danger-full-access` (no arg0 dispatch yet).
- `safety.rs` is patch-safety logic; its command part is just Codex's dangerous-command check, which ether takes through `exec_policy.rs`. Nothing else from it is ported for exec.
- `ether` asks for command approval on the terminal (`y`, `a` for the session, anything else aborts); without a terminal on stdin it declines. It prints commands, their output and exit status on stderr.
- Phase 4 reaches GLM through Zro's gateway (`https://zro.moonmath.ai/v1`, key in `ZRO_API_KEY`, Chat Completions), the endpoint the `zro` launcher configures for pi; it is a built-in `zro` provider and the default, with `glm-5.3` the default model. `openai` stays available with `-p openai`.
- Chat requests send instructions and developer items as `system` messages (pi's Zro config sets `supportsDeveloperRole: false`), fold each model response back into one `assistant` message with `reasoning_content` and the tool-call argument strings exactly as streamed, and send only function tools. Reasoning effort goes in `reasoning_effort`; whether Zro also wants Z.AI's `thinking` object is checked live.
- The GLM profile uses Zro's catalog values for GLM 5.2 (524,288-token window) until the live catalog gives 5.3's.
- `--request-log FILE` (was `--replay-log`) logs each request body in the provider's wire format, including under `--replay`, so `scripts/check-prefix.py` checks the cache prefix without a network.
- GLM 5.3's context window is the live catalog's 1,048,576 tokens. GLM requests send `thinking: {type: "enabled", clear_thinking: false}` (as the brief asks; Zro accepts it) and `reasoning_effort` only when configured; developer context stays as `system` messages, which Zro accepts mid-conversation.
- The live checks use the Zro key from pi's config (`~/.pi/agent`), at your instruction, passed only through the child process's environment and never printed or stored in the repo.
